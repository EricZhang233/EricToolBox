# 09 — INI 编码（T2）+ 一个被顺带挖出来的真 bug

| 项 | 值 |
|---|---|
| 目标 | T2：`GetPrivateProfileStringW` 到底能正确读回哪种编码的中文？ |
| 结论 | ✅ **只有 UTF-16LE + BOM 可用**。UTF-8（带不带 BOM）**都不能用**，而且失效方式不同、都**静默** |
| 副产品 | 🔴 **发现并修掉一个真 bug**：注入的幂等判定用"记住 Footer 指针"，而**分配器会复用地址** ⇒ 按钮**被静默跳过**（见 §6） |
| 日期 | 2026-10-03 |
| 环境 | Windows 11 build 26300.9550；系统 ACP = 936（GBK） |
| 探针 | `docs/poc/src/probes/initest.cpp`（5 种编码 × 读/写两侧）、`check-button-text.ps1`、`reopen-panel.ps1` |
| 复现 | 编码矩阵 1 次（确定性）；端到端中文渲染 3 次；幂等 bug 2 次 |

---

## 1. 为什么这项不能靠推理

INI 是**两个二进制之间的接口**（App 写 / TAP 读）。编码假设不一致时，结果**不是"读不到"**，
而是三种**都静默**的坏结果之一：

| 失效方式 | 表象 | 为什么难查 |
|---|---|---|
| 读到**乱码** | 按钮上显示 `éŸ³é‡?` 之类 | 一看就知道不对，但要怀疑到"编码"上得懂 INI 的 ACP 行为 |
| **键都找不到** | 静默回落到默认值（按钮显示默认文字） | **看上去完全正常** —— 谁会想到"我的设置被忽略了"是因为 BOM 字节？ |
| **换台机器才坏** | 本机全对 | 只在 ACP 非 936 的机器/系统区域设置上暴露 |

`GetPrivateProfileStringW` 是 W 版 API，容易让人误以为"它就是 Unicode 的、随便什么编码都行"。**不是。**

---

## 2. 方法

`initest.cpp` **手工构造字节**（不经任何编码转换），对同一份内容（`[t]` / `k=音量合成器测试`）
生成 5 种编码的文件，再用 `GetPrivateProfileStringW` 读回。

三个刻意的设计：

1. **用码点（`\uXXXX`）打印结果**，不用 `%ls` —— 否则"控制台/重定向的编码"会再乱一次，
   分不清是 API 读错还是日志打错。
2. **打印文件前 26 字节的 hex** —— 让测试**自证**写进去的字节确实是我以为的那些。
   > ★ 这不是多余的：**第一版测试就是错的**，我把 UTF-16LE 的高位字节写死成 0
   > （`push((char)wchar); push(0);`），于是 `U+97F3` 被写成 `F3 00` 而不是 `F3 97`，
   > 结果 UTF-16LE 两例全报乱码 —— 差点得出"文档推荐的编码也不对"的**反向错误结论**。
   > 加了 hex dump 之后一眼看出。**编码测试必须能自证字节。**
3. **区分"键找不到"与"内容乱码"** —— 缺省值设成 `<KEY-NOT-FOUND>` 哨兵，两者失败机理完全不同。

---

## 3. ✅ 读侧结果（核心表）

| # | 编码 | 文件前几字节 | 读回 | 结论 |
|---|---|---|---|---|
| 0 | **UTF-16LE + BOM** | `FF FE 5B 00 74 00 5D 00 …` | `\u97F3\u91CF\u5408\u6210\u5668\u6D4B\u8BD5` | ✅ **正确** |
| 1 | UTF-16LE **无** BOM | `5B 00 74 00 5D 00 …` | `\u9AFC\u880E\u0008T\u0010bhVKm\u8ACE` | ❌ 乱码（被当 ANSI 读） |
| 2 | UTF-8 **+ BOM** | `EF BB BF 5B 74 5D …` | `<KEY-NOT-FOUND>` | ❌ **键都找不到**（BOM 污染了节名 `[t]`） |
| 3 | UTF-8 无 BOM | `5B 74 5D 0D 0A 6B 3D E9 9F B3 …` | `\u95CA\u62BD\u567A\u935A\u581F\u579A\u9363\u3126\u7974\u7487` | ❌ **静默乱码**（ASCII 节名/key 能匹配，值全错） |
| 4 | 系统 ACP（本机 GBK） | `5B 74 5D 0D 0A 6B 3D D2 F4 C1 BF …` | `\u97F3\u91CF\u5408\u6210\u5668\u6D4B\u8BD5` | ⚠️ 本机正确，**只因 ACP=936** ⇒ 不可作为契约 |

⇒ **只有 UTF-16LE + BOM 与系统区域设置无关。**

---

## 4. ✅ 写侧另有一个坑：`WritePrivateProfileStringW` 会把**全新文件**写成 ANSI

| 场景 | 实测 |
|---|---|
| **[A]** 对一个**不存在**的文件调 `WritePrivateProfileStringW` | ⚠️ 生成的文件**没有 UTF-16 BOM**，是 ANSI（本机 GBK 字节：`D2 F4 C1 BF …`）。本机读得对，**换区域设置就乱** |
| **[B]** 对**已存在且带 BOM** 的文件再写键 | ✅ 保持 UTF-16LE（BOM 保留），两个键都读得对 |

⇒ **C++ 轨道的 `Ini::WriteAll` 必须自己写 BOM 与 UTF-16LE 字节**，不能图省事把整个写侧
委托给 `WritePrivateProfileStringW`。后者只适合"文件已是 UTF-16LE 时改键"。
这也正是"把写做成唯一入口"的价值 —— 这个坑只需要在一个地方挡掉。

## 5. ✅ 端到端：按钮文字真的变成中文

编码层对了不代表链路对了，所以补一次真实渲染：把 `vcxtap.ini` 写成 **UTF-16LE + BOM**、
`entry1_text=音量合成器`，开面板后读按钮的 UIA `Name`：

```text
[4] name=音量合成器  code=\u97F3\u91CF\u5408\u6210\u5668  rect=(2451,1419 92x40)
期望码点 = \u97F3\u91CF\u5408\u6210\u5668
RESULT: PASS
```

* 文字**逐码点一致**（说明 `GetPrivateProfileStringW` 在 ShellHost 里读中文没问题）。
* 位置 `(2451,1419 92x40)` ⇒ 右边缘 `2451+92 = 2543` = 面板右 2547 − 4，**右对齐未受影响**。
* 宽度 92（比 `TestLink` 的 71 宽）—— 中文按钮更长，说明布局是按内容自适应的。

> 比较是在**进程内**做的（PowerShell 内部 UTF-16），只输出 ASCII 的 `PASS/FAIL` + 码点 ——
> 避免"子进程 stdout 的编码"把结论搞脏。见 `check-button-text.ps1`。

## 6. 🔴 副产品：幂等判定用"记住指针"是错的（已修）

做 §5 的时候按钮**压根没出现**。查日志：

```text
[03:15:12.133] *** Footer appeared: … handle=2A2C2B97DD8      → 注入了
[03:19:14.412] *** Footer appeared: … handle=2A2C2B97DD8      → 什么都没发生
```

**同一个 handle。** 面板关了又开、XAML 元素确实重建了，但**分配器把同一地址复用给新对象**。
而当时的幂等守卫是：

```cpp
static void* g_lastInjectedFooter = nullptr;
if (g_lastInjectedFooter == winrt::get_abi(footer)) return;   // ← 裸 return，连日志都没有
g_lastInjectedFooter = winrt::get_abi(footer);
```

于是新树被误判成"已处理"，**按钮被静默跳过**。

> ⛔ 交付文档里原话是"面板每次打开重建元素、**句柄会变，所以不会误判**"。
> 前半句对，后半句错 —— 元素重建 ≠ 地址不同。**这句话写在两份文档里，现已改正。**

### 6.1 修法：让判据自证

```cpp
// 给按钮打标记
WUXA::AutomationProperties::SetAutomationId(btn, L"VmExtEntry");

// 幂等判定：问"结果在不在"，而不是"我记不记得做过"
if (FindOurEntry(footer, 0)) { LogF("…已有我们的按钮 -> 跳过（内容判定）"); return; }
```

好处不止"修好这一个 bug"：

| 好处 | 说明 |
|---|---|
| 结构性正确 | 判据不再依赖任何外部状态，地址复用骗不到它 |
| **自愈** | 若按钮被 XAML 重新模板化移除，下一次 Footer 事件会**重新注入**（指针守卫会永久阻断） |
| 可观测 | 跳过时**有日志**（原来那条 `return` 是静默的，所以第一次排查时毫无线索） |
| 顺带利于验收 | `AutomationId` 让脚本能精确定位按钮，不必"按会变的文字找" |

### 6.2 验证

| 检查 | 结果 |
|---|---|
| 肇事变量是否彻底移除 | ✅ `g_lastInjectedFooter` / `get_abi(footer)` 在源码里 0 处引用（只剩注释里的历史说明） |
| 树真的重建后能否再注入 | ✅ `Footer appeared` 次数 1 → 2，新 handle `1E78BED67B8`（与旧的 `1E7892A5DA8` 不同），**注入成功** |
| 中文文字 + 几何 | ✅ `音量合成器`、右边缘 2543 |

> ⚠️ **没做到的**：没能**确定性地**再撞一次"地址完全相同"的情形来复跑。分配器复用地址本身就是竞态，
> 脚本化的"关-开面板"也不可靠（`Win+Ctrl+V` 不是开关；`Esc`/`Win+A`/`Win+D` 都关不掉；
> band=4 窗口的状态判断骗过我两次 —— 见 §7）。
> 但修复是**结构性**的：那个状态变量已经不存在，判据不看地址 ⇒ 该失效模式**不可达**。
> 这比"再撞一次巧合"是更强的保证。

## 7. 踩到的测试陷阱（留给以后，免得再浪费一轮）

| 陷阱 | 现象 | 正解 |
|---|---|---|
| `Win+Ctrl+V` 是"打开声音输出页"，**不是**开关 | 面板已开着时它是空操作；于是"多轮测试"实际一直在读**同一个树**，看起来每轮都通过 | 关面板要用别的办法（点击别处 / 让浮层失焦），并且**用日志验证树真的重建了**（`Footer appeared` 计数增加） |
| `IsWindowVisible` 判断面板开没开 | band=4 的 HWND **常驻**，一直返回 true | 不可用 |
| 用前台窗口类名判断 | ✅ 实测被它骗过：`Esc` 之后仍报 on-top | 也不可靠 |
| **用 TAP 自己的日志当判据** | — | ✅ **唯一可靠的**：`Footer appeared` 是否新增，即"树被重建"的直接证据 |
| 读侧测试不打印字节 | 第一版 UTF-16LE 构造错了都不知道，差点得出反向结论 | 打印文件前若干字节的 hex |

## 9. 本项**没有**覆盖的部分

* **不通过 `GetPrivateProfileStringW` 的读取路径**：比如将来改用自写 INI 解析器，本结论不适用（那时 UTF-8 反而是好选择）。
* **`Ini::SelfTest` 在产品启动自检里的实际表现**（C++ 轨道）：本项验证的是 OS 行为，不是那段自检代码。
* **字体/渲染层**：本项只证明"读到的字符串是对的"（码点逐位一致）；字形是否漂亮、是否缺字不在范围内。
* **非中文的其他非 ASCII**（如 emoji、代理对）：只测了 BMP 内的 7 个汉字。
